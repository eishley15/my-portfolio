Kyle Payawal Studio · Client Gallery · Proposal

Share links, without the code.

Six ways to let a client open their gallery from one tap, without making it guessable or easy to leak. Three are modelled on Google Drive sharing. Three use other approaches. Each one has a diagram, how it works, the trade-offs, and scores, followed by a recommendation for this codebase.

How it works today

Code → JWT → gallery

  • Client types an access code on AccessGate.jsx.
  • /api/gallery-auth looks it up in clients (checks is_active, expires_at) and returns a 7-day JWT holding { accessCode }.
  • The JWT is stored in localStorage and every gallery API verifies it.

Things to watch

  • The access code is the password and the primary key. Putting it in a URL makes the code public. Share links need their own separate token.
  • The JWT only carries accessCode, so you can't revoke one shared link without changing the client's code.
  • /slideshow/:accessCode and the legacy ?accessCode= path in download.js already put the code in URLs.
  • The rate limiter lives in memory, so every serverless instance starts with a fresh count.

Part A

Google Drive–style

Drive's sharing panel has three settings: who can open the link (anyone or specific people), what they can do (role), and whether you can switch it off later. Each concept below takes one of those settings.

01

Anyone with the link

A long random link that works for whoever has it. You can turn it off, and it can expire. This is how Drive's "Anyone with the link" works.

Drive · Public link

How it works

  1. In Studio, click Create share link. The server generates a 32-byte random token and stores only its SHA-256 hash in a new gallery_share_links table.
  2. Opening /g/<token> calls /api/gallery-share, which checks the hash, revocation, and expiry, then issues the same gallery JWT you use now, with a new shareId claim added.
  3. The token is removed from the address bar right away (history.replaceState), and the page sends Referrer-Policy: no-referrer and noindex.
  4. Revoke sets revoked_at. Gallery APIs reject any JWT whose shareId has been revoked.
Pros
  • One tap for the client
  • Simplest to build on your stack
  • Each link can be revoked and given an expiry
Cons
  • Anyone the link is forwarded to gets in
  • Links can leak through chat previews and screenshots

Scores

Security3/5
Client ease5/5
Build ease4.5

Best for: most sessions, like events, couples, and brand shoots, where the client wants to forward the gallery to family anyway.

02

Restricted: invited people only

The link only works for email addresses you've added. A visitor proves they own the email with a one-time code. This is Drive's "Restricted" setting.

Drive · Restricted

How it works

  1. Add a gallery_viewers table (client_code, email). Kyle adds one or more emails per gallery.
  2. A visitor enters their email. If it's on the list, Resend (already set up) emails a 6-digit code or one-click magic link that expires in 10 minutes.
  3. Show the same "check your inbox" screen whether or not the email is on the list, so the page never confirms who's invited.
  4. A verified device gets a 30-day session cookie, so the client verifies only once per device.
Pros
  • A forwarded link does nothing on its own
  • You know who viewed (email audit trail)
  • No code to remember
Cons
  • One extra step for the client
  • Email deliverability becomes critical
  • Kyle has to collect guest emails

Scores

Security5/5
Client ease3/5
Build ease2.5

Best for: sensitive work like boudoir, maternity, family with kids, and corporate under NDA.

03

Role-based links

One gallery, several links, each with its own permissions. This is Drive's Viewer / Commenter / Editor dropdown, mapped to what photo clients actually do.

Drive · Roles

How it works

  1. Concept 01's table gets a role column (view | pick | owner). Studio shows a "Share" panel with one row per link.
  2. The role goes into the JWT. download.js, download-zip.js, and gallery-favorites.js each check it before doing anything.
  3. If a guest link leaks, the most anyone can do is view web-size photos. Full-res files stay limited to the owner link.
Pros
  • Each person gets only the access they need
  • Easy for clients to share with guests
  • Builds directly on 01
Cons
  • More links for Kyle to manage
  • The owner link still works for anyone who has it

Scores

Security4/5
Client ease5/5
Build ease3.5

Best for: weddings and events, where the couple wants guests to browse but only they should download.

Part B

Other approaches

These don't follow the Drive model. Each borrows from a different field: photo delivery platforms, signed CDN links, and device pairing.

04

Link + PIN, sent separately

The link arrives in one message and a short 4-digit PIN in another. A leaked link alone isn't enough. Photo delivery platforms often use a similar PIN to gate downloads.

Two-part key

How it works

  1. Each share link gets an optional pin_hash (bcryptjs is already installed).
  2. Variant A: the PIN is required to open the gallery. Variant B: the link opens the gallery for viewing, and the PIN is only asked for on download. Variant B is closer to how photo delivery platforms usually work.
  3. Count failed attempts per link in Supabase rather than memory, so the lockout survives cold starts.
Pros
  • A forwarded link alone isn't enough
  • 4 digits is easy to type
  • Small change on top of 01
Cons
  • Only protects if the PIN goes through a different channel
  • 4 digits needs strict lockout to be safe

Scores

Security4/5
Client ease4/5
Build ease4/5

Best for: protecting full-res downloads while keeping viewing to one tap.

05

Signed, self-expiring URL

The link carries its own expiry date and a cryptographic signature, so there's nothing to look up in the database. It works the same way as S3 presigned URLs and signed CDN links.

Stateless

How it works

  1. The link is a short-form JWT/HMAC signed with DOWNLOAD_TOKEN_SECRET, the same mechanism your download tokens already use.
  2. The server only verifies the signature and checks the expiry. There's no new table.
  3. To revoke a link early, you'd need a deny-list, which brings back a database table, so it ends up like concept 01.
Pros
  • Least code of any option, no migration
  • Expiry is built into the link
Cons
  • Can't revoke a single link
  • No view tracking
  • Long, ugly URLs

Scores

Security2.5
Client ease5/5
Build ease5/5

Best for: short-lived links, like a 48-hour "sneak peek" or the slideshow URL. Not a good fit for the main gallery.

06

Claim-once link (device binding)

The first device that opens the link claims it. After that, the link stops working on new devices unless the client approves them. Netflix-style device pairing works the same way.

Key that locks

How it works

  1. On first open, the server binds the link to that browser with a long-lived httpOnly cookie (or, optionally, a passkey) and records it in share_link_devices.
  2. Each link gets a device limit, for example 3. Once all slots are used, a new device triggers an approval email to the owner.
  3. Kyle can see claimed devices in Studio and remove any of them.
Pros
  • A leaked link becomes useless once it's claimed
  • No codes or emails for the first open
Cons
  • A cleared browser counts as a "new device"
  • If someone else opens the link first, they claim it
  • Most complex flow and the most support questions

Scores

Security4.5
Client ease3.5
Build ease2/5

Best for: high-value deliveries where the client uses one or two devices.

Recommendation

Combine 01 + 03 + 04 into one share panel

These three are really one feature: a share link with a role, an expiry, a revoke button, and an optional download PIN. All of them use a single new table and reuse your existing JWT flow. Add concept 02's "Restricted" mode later as a per-gallery toggle for sensitive sessions.

Phase 1

Share link

  • gallery_share_links table
  • /g/:token route + /api/gallery-share
  • Studio: create / copy / revoke / expiry
  • Gallery APIs check shareId isn't revoked

Phase 2

Roles + PIN

  • role: view / pick / owner
  • Download endpoints enforce role
  • Optional bcrypt PIN on downloads
  • Lockout counter in Supabase

Phase 3

Restricted mode

  • Invite list per gallery
  • Email code via Resend
  • Toggle: "Anyone with link" / "Restricted"
  • View log (who / when)

Sketch of the table

create table gallery_share_links (
  id           uuid primary key default gen_random_uuid(),
  client_code  text not null references clients(access_code)
               on delete cascade,
  token_hash   text not null unique,   -- sha256, never the raw token
  role         text not null default 'owner'
               check (role in ('view','pick','owner')),
  pin_hash     text,                   -- optional, bcrypt
  expires_at   timestamptz,
  revoked_at   timestamptz,
  failed_pins  int  not null default 0,
  last_used_at timestamptz,
  created_at   timestamptz not null default now()
);
alter table gallery_share_links enable row level security;
revoke all on gallery_share_links from anon;

Security checklist

  • Token = 32 bytes from crypto.randomBytes, base64url
  • Store only the SHA-256 hash, so a database leak doesn't expose working links
  • Exchange the token for a JWT once, then remove it from the URL
  • Referrer-Policy: no-referrer + X-Robots-Tag: noindex on /g/*
  • JWT carries shareId + role, and is checked against revoked_at
  • Shorter JWT lifetime for share sessions (e.g. 24h, auto-refreshed)
  • Never log full URLs containing tokens
  • Same generic error for invalid, revoked, and expired links
  • Also: stop putting the access code in /slideshow/:accessCode
